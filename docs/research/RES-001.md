# RES-001 — протокол исследования Telegram

**Дата подготовки:** 28 сентября 2026 года
**Состояние:** инструмент и автоматические проверки подготовлены; проверки в настоящем Telegram **не выполнялись** — в среде нет токена, тестовых чатов и Android/iOS/Desktop устройств. Исследование RES-001 не завершено.

## Источники и виды доказательств

Официальные источники, предназначенные для перепроверки перед прогоном (дата последней попытки доступа: 28 сентября 2026 года):

- [Telegram Bot API](https://core.telegram.org/bots/api): `getMe`, `getWebhookInfo`, long polling/`allowed_updates`, message entities, `getChatMember`, `message_thread_id`, reply parameters и ошибки API.
- [Telegram Bots FAQ](https://core.telegram.org/bots/faq): Privacy Mode и видимость сообщений.
- [aiogram documentation](https://docs.aiogram.dev/): aiogram 3.x, dispatcher и polling.

Из текущей среды источники и PyPI получить не удалось (HTTP 401/403 прокси), поэтому их содержимое не выдаётся за повторно подтверждённое. Версия `aiogram==3.22.0` закреплена как известный стабильный выпуск 3.x, совместимый с Python 3.12; чистую сетевую установку владелец должен подтвердить. Это решение только для probe.

Статусы ниже строго разделяют: **автотест** (управляемая модель без Telegram), **Telegram-наблюдение** (только фактический ручной прогон) и **не выполнялась**. Автотест probe не закрывает продуктовую приёмку A03/A05/A09/A16–A18/A26 на целевой БД и инфраструктуре.

## R1 — доставка обращений и Privacy Mode (A03, A18)

**Предпосылки:** настоящий username получен строкой старта после `getMe`; один разрешённый тестовый чат, один оператор, один назначенный участник.
**Матрица прав:** повторить с (1) обычным участником/Privacy ON, (2) обычным участником/Privacy OFF, (3) администратором; права и настройку записать фактически.
**Шаги:** в каждом режиме отправить `@ActualBot #probe`, `@ActualBot @probe`, голую `#probe`, `@OtherBot #probe`, пояснение с поздним `@ActualBot`, пересланное сообщение, затем отредактировать прежнее сообщение; отдельно разместить похожий текст в quote, `code` и `pre`. Проверить журнал только по метаданным и сопоставить, какие сообщения реально пришли боту. Reply/quote исходного сообщения не считать новым текстом команды. Добавить кириллицу и emoji перед/после entities и проверить UTF-16 offsets. Отправить от бота и от анонимного/неидентифицируемого отправителя, если режим доступен.
**Ожидание probe:** два первых варианта дают одинаковый состав; остальные не создают операцию. Отредактированные updates не зарегистрированы обработчиком. Неидентифицируемый отправитель и бот игнорируются.
**Автотест:** варианты, межчатовая изоляция, forwarding, бот/author, HTML и UTF-16 entity guards проверяются `test_probe.py`; фактическая доставка Telegram не моделируется.
**Наблюдение/status/вывод:** не выполнялась — нет Telegram-доступов.

## R2 — ID-упоминание и клиенты (A05)

**Предпосылки:** участник без username написал сообщение; оператор назначил его reply-командой.
**Права/Privacy:** записать для каждого режима R1.
**Шаги:** вызвать обе формы; на Android, iOS и Desktop отдельно записать отображаемое имя, открывается ли профиль, было ли фактически видимое/звуковое уведомление при заданных настройках и состоянии приложения. Повторить с именем, содержащим `<`, `&`, кириллицу и emoji.
**Ожидание probe:** ссылка использует числовой `tg://user?id=...`, имя безопасно экранировано, обе формы адресуют тот же ID. Push не гарантируется.
**Автотест:** построение ID-ссылки и экранирование пройдены локально.
**Наблюдение/status/вывод:** не выполнялась — нет трёх клиентов и тестового аккаунта без username.

## R3 — темы, reply и несколько частей (A09, A16, A17)

**Предпосылки:** forum topic, 2–3 назначенных аккаунта, `PROBE_CHUNK_SIZE=1`, `PROBE_CHUNK_DELAY_SECONDS=3`–10.
**Права/Privacy:** записать фактические права; повторить минимум для требуемого production-кандидатом набора.
**Шаги:** (a) вызвать в теме и проверить каждую часть; (b) между частями закрыть тему; (c) отдельно удалить исходное сообщение; (d) между частями вывести следующего участника из чата; (e) вернуть его и вызвать снова без назначения.
**Ожидание probe:** каждая попытка содержит исходные thread/reply IDs; при невозможности отправки нет fallback в общий чат; событие выхода и `getChatMember` исключают адресата из ещё не отправленной части; возврат не восстанавливает назначение. Ошибку API заранее не предсказывать — фиксировать фактический ответ и влияние прав. Между `getChatMember` и `sendMessage` остаётся гонка: статус может измениться после проверки.
**Автотест:** контекст reply/topic, выход между частями и отсутствие восстановления проверены управляемым транспортом. Закрытие темы и удаление сообщения требуют Telegram.
**Наблюдение/status/вывод:** не выполнялась — нет forum-чата.

## R4 — membership updates и права (A09)

**Предпосылки:** polling запущен с явно заданными `allowed_updates=[message, chat_member]`.
**Шаги:** записать получение `chat_member` при выходе/бане/возвращении; вызвать `getChatMember` для участника при разных правах бота; сравнить полученные события и ответы API. Не создавать массовую нагрузку.
**Ожидание probe:** полученное событие выхода блокирует будущую часть; возврат удаляет старое назначение. Полнота updates и доступность `getChatMember` считаются наблюдением, а не предположением.
**Автотест:** строковые и Enum-представления статусов, обе формы `restricted`, переход из `restricted/is_member=false` в присутствие без восстановления назначения, отказ назначения отсутствующему/непроверенному участнику и игнорирование событий чужого чата проверяются моделями aiogram и Dispatcher; доступность настоящих API/updates не проверена.
**Наблюдение/status/вывод:** не выполнялась — нет бота/чатов.

## R5 — неопределённая отправка (A26)

**Предпосылки:** только управляемый fake transport, без искусственного ограничения Telegram.
**Шаги:** транспорт записывает принятую отправку и затем бросает `TimeoutError`; повторить тот же входящий update. Перезапустить процесс отдельно.
**Ожидание probe:** результат `uncertain`, автоматического повтора части нет; повтор update в текущем процессе не отправляет снова. После перезапуска память потеряна, поэтому повтор возможен: probe **не доказывает** надёжность будущей постоянной очереди.
**Автотест:** выполнен `test_timeout_is_uncertain_and_duplicate_update_is_not_resent`; одна попытка отправки. Отдельные проверки подтверждают безопасную диагностику этапа, класса ошибки и результата без текста исключения, сообщения или токена.
**Telegram-наблюдение:** не требуется и намеренно не провоцируется.
**Статус/вывод:** автоматическая модель подготовлена; продуктовый A26 остаётся `не выполнялась`.

## Действия владельца и критерий завершения

1. Установить probe в чистом Python 3.12 окружении по [инструкции](../../experiments/telegram_probe/README.md), подтвердить разрешение версии из package index.
2. Создать изолированного бота/чаты, получить ID встроенным discovery-режимом, затем включить allowlists.
3. Выполнить R1–R4 с обезличенными артефактами и заполнить паспорт/наблюдения для Android, iOS, Desktop.
4. Сопоставить наблюдения с официальной документацией на дату прогона и оформить выводы для будущих P0 задач.

Сейчас готов **только инструмент исследования**. RES-001 завершится лишь после реальных прогонов, заполнения наблюдений и выводов; продукт и его приёмка при этом всё равно не считаются готовыми.
